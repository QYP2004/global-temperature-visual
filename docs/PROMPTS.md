# 核心 Prompt 记录

> 以下记录引导 AI 开发的最核心原始 Prompt，并标注其对应的开发范式阶段。

---

## 阶段一【SDD：数据建模与 API 契约】

**原始 Prompt：**
> 设计「AI 圆桌演播厅」的领域模型与 API 契约。实体至少包含 Discussion / Guest / Message / Consensus / Divergence。先输出 Mermaid ER 图，再给出表结构与 REST 路由契约：讨论列表、创建讨论、讨论详情、启动讨论、SSE 事件流。要求多场讨论并行时状态与事件流互相隔离，讨论状态机为 pending→active→ended。

**说明：** 意图是"先定契约再写代码"，避免边写边改数据形状。挑战在于"实时状态（待机/发言中）到底落库还是放内存"——引导 AI 把它定为瞬态、由事件流重建，而不是塞进数据库。

---

## 阶段二【DDD：前端组件与页面】

**原始 Prompt：**
> 基于演播厅视觉风格实现三个区域：左侧嘉宾席小窗（色块 + 状态徽章 + 公开思考摘要）、中间现场实录（发言人气泡，按专家颜色区分）、右侧共识与分歧面板。要求中文 UI、响应式三栏→两栏→单栏，每个区域在自身容器内独立滚动，不依赖整页滚动；通过 SSE 订阅实时更新。

**说明：** 挑战是窄屏下既要独立滚动又不能整页抖动。引导 AI 用 CSS Grid 做布局骨架、每个面板 `overflow-y:auto`，并把"状态徽章/思考摘要"抽象成可复用的小窗组件，而不是写死在页面里。

---

## 阶段三【TDD：核心逻辑测试先行】

**原始 Prompt：**
> 为三个核心 Agent 先写测试：① 嘉宾生成——校验专家人数、主持人必填、颜色由后端分配；② 发言调度——speaker_id 必须在嘉宾列表内、拒绝空发言、未知 action 回退 comment；③ 共识提炼——短于 2 条发言返回空、结果去重。用一个可注入的 FakeLLM 脚本化返回，不依赖真实模型。

**说明：** 挑战是大模型输出不可控、无法稳定断言。引导 AI 把 LLM 抽象成 `LLMClient` 协议，测试用脚本化假对象，让"契约校验"成为可单测的纯函数——这一步直接决定了后面业务实现敢不敢重构。

---

## 阶段四【业务实现：三个核心 Agent】

**原始 Prompt：**
> 实现三个 Agent：① 生成主持人+立场多元专家阵容；② 每轮把完整 transcript 交给大模型，让它决定"下一位发言者 id + 1~2 句台词 + 公开思考 + 动作类型"，禁止机械轮流；③ 每 2 轮从发言中提炼共识与分歧。所有大模型调用都要求返回结构化 JSON，并在代码里做容错解析。

**说明：** 挑战是大模型偶尔返回带 Markdown 或多余文字的 JSON。引导 AI 写一个"容忍代码块/截取最外层花括号"的解析器，并把"非机械轮流"作为 Prompt 的硬约束写进契约，而不是靠后处理。

---

## 阶段五【E2E：系统级端到端测试】

**原始 Prompt：**
> 用 httpx ASGITransport 起真实 FastAPI 应用写 E2E：创建讨论→启动→轮询直到 ended，断言发言条数、共识/分歧被写入、总结是自然语言且不含 JSON。再写一个并行隔离测试：两场讨论同时启动，断言各自 transcript 不串台。

**说明：** 遇到的坑是 FakeLLM 用 FIFO 队列时，两场并发讨论把脚本顺序打乱导致假失败。引导 AI 把假对象改成"按 Prompt 内容路由"（看到阵容请求就回阵容、看到调度请求就回发言），并发下依然确定。

---

## 阶段六【真实模型接入与错误治理】

**原始 Prompt：**
> 接入真实大模型：API Key 只从后端环境变量读取；加可配置超时与自动重试；把超时/连不上/Key 无效/限流翻译成中文可读错误；兼容只支持 Responses API 的本地中转。

**说明：** 真实环境踩了两个坑——直连 api.openai.com 超时、本地中转只认 `/v1/responses` 而不是 `/v1/chat/completions`。引导 AI 在 LLM 客户端里加 `wire_api` 分支，用同一套业务代码适配两种协议，而不是为中转写第二套后端。
