# 开发过程与工作流说明

## 1. 工具链与协作方式
本项目在 **Claude Code**（Vibe Coding 工具）中开发，模型侧通过兼容 OpenAI 协议的 **DeepSeek V4 Pro** 提供能力。协作节奏不是"一句话生成整个项目"，而是按范式分阶段推进：

1. **SDD 阶段**：先用一段 Prompt 锁定领域模型与 API 契约（ER 图 + 路由），产出 `docs/PRD.md`、`docs/ER.md`。契约不定不动手写业务。
2. **TDD 阶段**：针对三个核心 Agent（嘉宾生成、发言调度、共识提炼）先写测试，用可注入的 FakeLLM 脚本化返回，让纯逻辑可断言。
3. **业务实现阶段**：按已通过的测试去实现，Prompt 集中放在 `backend/prompts.py`，结构化 JSON 契约驱动。
4. **DDD 阶段**：前端按演播厅视觉拆成嘉宾席/实录/共识分歧三个区域，SSE 驱动状态流转。
5. **E2E 阶段**：用 httpx ASGITransport 起真实应用做端到端与并行隔离测试，形成质量闭环。

## 2. 典型问题与解决路径

**问题一：大模型请求超时。**
现象是"嘉宾生成失败：Request timed out"。排查发现当前网络直连 api.openai.com 被污染不可达。解决：切换到国内可达端点，并在 LLM 客户端加 `LLM_TIMEOUT` / `LLM_MAX_RETRIES`，把超时、连接失败、Key 无效、限流翻译成中文可读错误，而不是把英文堆栈抛给用户。

**问题二：本地中转只支持 Responses API。**
接入本机中转时 `/v1/chat/completions` 返回 404，因为它只认 `/v1/responses`。解决：在 `OpenAILLM` 里加 `wire_api` 分支，Chat Completions 与 Responses 两套调用共用同一套业务代码与 JSON 解析，不为中转写第二套后端。

**问题三：并发 E2E 测试假失败。**
两场讨论同时跑时，脚本化 FakeLLM 的 FIFO 队列被并发请求打乱顺序，导致断言失败。解决：把假对象从"按顺序吐"改成"按 Prompt 内容路由"——看到阵容请求回阵容、看到调度请求回发言，并发下依然确定。

## 3. 对"工程化 AI 开发"的理解
- **先契约后代码**：让 AI 先产出可评审的 ER 图、API 契约、Prompt 契约，再生成实现，能大幅减少"生成即返工"。
- **把不确定性关进测试**：大模型不可控，就把它抽象成接口，用脚本化假对象让核心逻辑可单测；真实模型只在 E2E 与冒烟里出现。
- **分阶段切换范式**：SDD 管数据边界、TDD 管核心逻辑、DDD 管组件结构、E2E 管系统闭环，不同阶段用不同的 Prompt 策略，而不是一条 Prompt 硬刚到底。
- **Prompt 是一等工程资产**：集中管理、结构化输出、带容错解析，而不是散落在代码里的字符串拼接。
